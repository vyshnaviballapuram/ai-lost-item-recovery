AI-Based Campus Lost-Item Recovery System

Engineering Specifications, Algorithm Design & Administrative Verification Logic

1. AI Matching Engine Architecture

The AI matching engine is implemented in a dedicated modular service (items/services/ai_matching.py). Unlike traditional simple text search engines, it utilizes a composite, multi-factor scoring function:

Feature Component Weight Evaluation Method Description
Textual Similarity 45% TF-IDF & Cosine Similarity Evaluates n-grams across combined titles and descriptions using Scikit-Learn vectorization.
Category Hierarchy 20% Hierarchical Classification Matches primary category, subcategory tokens, and device classifications.
Distinctive Attributes 15% Token Overlap & Penalty Filter Detects matching brands, color descriptors, and private sticker identifiers while penalizing contradictory colors.
Campus Location 10% Landmark & Zone Proximity Correlates buildings, campus reading zones, library wings, and dining halls.
Temporal Timeline 10% Chronological Coherence Verifies chronological coherence: lost date must realistically precede or align with found date.
Similarity Score Notice: The score represents a normalized similarity metric (0 to 100), not an automated determination of legal ownership. Final recovery always requires human administrative verification.

2. Administrative Approval & Verification Workflow

Our architecture enforces a rigorous, state-machine driven approval process:

PENDING

Initial state for all user reports. Completely hidden from public catalog and external queries.

NEEDS_INFORMATION

Admin contacts student requesting clarification on identifiers or specific location markers.

APPROVED

Verified by campus staff. Only at this point is the report eligible for sanitized public listing.

REJECTED / ARCHIVED

Deactivates all recovery suggestions and keeps report hidden without deleting database audit history.

3. Security & Engineering Best Practices

  • IDOR Protection: Users can never access other students' pending or unapproved reports by tampering with URL parameters or report IDs.
  • CSRF & Authentication: Strict CSRF validation on all POST actions; session security cookies; rate-limited logins.
  • Database Constraints: Unique constraint prevents duplicate match-pairs (lost_report, found_report).
  • Dual Interface Separation: Technical Django Admin is isolated for database administrators, while staff use a modern SaaS Operations Console.
  • Deployment Ready: Pre-configured with WhiteNoise, PostgreSQL dj-database-url, and Gunicorn for 1-click deployment on Render.
